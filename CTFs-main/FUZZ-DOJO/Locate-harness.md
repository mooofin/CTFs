This challenge introduces how fuzzing is used in real open source projects and how fuzzing harnesses are identified. Fuzzing works by repeatedly feeding random input into a program to trigger crashes, hangs, or other unintended behavior. Random data alone is not enough to reach meaningful code paths, so developers write fuzz drivers, also called fuzzing harnesses. These are small entry points that take raw bytes from the fuzzer and pass them into real library functions in a way that exercises complex logic.

The first step in the challenge was running `/challenge/build`, which compiled the minizip project with fuzzing enabled. The build output was important because it revealed where the fuzz drivers were located. The logs showed that files such as `unzip_fuzzer.c`, `zip_fuzzer.c`, and `new_fuzzer.c` were being compiled as fuzz targets. During the build process, these files were also copied into a persistent directory under `~/fuzz-dojo/training-locate`, which is where the challenge expects the user to examine them.

At first, accessing the fuzz files failed because the working directory was incorrect. The shell was in `/home/hacker`, while the fuzz drivers were stored in `~/fuzz-dojo/training-locate`. After changing into that directory, the fuzz driver source files were visible. Opening `unzip_fuzzer.c` confirmed that it contained a function named `LLVMFuzzerTestOneInput`, which is the standard entry point used by libFuzzer. Instead of a `main` function, libFuzzer repeatedly calls this function with arbitrary byte buffers.

Looking at the implementation of `LLVMFuzzerTestOneInput` showed how the harness works in practice. The function creates an in-memory stream, feeds the fuzz input into it, and then calls minizip’s ZIP parsing routines as if the data were a real archive. It walks through metadata, file entries, encryption paths, and archive comments. The goal is not correctness, but coverage. If malformed input causes a crash, memory corruption, or infinite loop, the fuzzer detects it and reports a bug.

After identifying a file that clearly contained a fuzz driver, the solution was submitted using `/challenge/training unzip_fuzzer.c`. This satisfied the requirement of locating a fuzz harness, and the challenge returned the flag `pwn.college{ElF89wF6eNa36jEe21B5GTb6DRG.dVDOyUDL0ATO0czW}`.
